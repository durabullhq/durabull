# Contributing to Durabull

Documentation improvements, bug fixes, and focused features are welcome. Read the
[Code of Conduct](CODE_OF_CONDUCT.md) and [license](LICENSE) before contributing.

## Set up a development environment

Use Bun `1.3.5` and Node.js `20.19+` or `22.12+`. The
[local development guide](apps/docs/content/documentation/getting-started/local-development.mdx)
covers a minimal authless setup and a full seeded stack.

```bash
git clone https://github.com/durabullhq/durabull.git
cd durabull
bun install --frozen-lockfile
git switch -c docs/describe-your-change
```

Choose a branch name that describes your work. Keep real credentials, generated files, screenshots
used only for debugging, and personal notes out of commits.

The MCP distribution has a narrow generated-file exception: commit its self-contained app bundle
(`packages/mcp/src/apps/dashboard.generated.txt`) and Claude compatibility manifests under
`plugins/durabull`. Source-mode deployments and plugin installation consume these files directly.
Edit their source files, regenerate with `bun run mcp:app` / `bun run mcp:plugin`, and run
`bun run mcp:check` to prove that committed distribution assets are current. Do not commit local
preview screenshots or browser logs.

## Edit the documentation

Public guides live in `apps/docs/content/documentation/` as MDX. Every page needs `title` and
`description` frontmatter. Sidebar order comes from `meta.json`; add new public guides there.
Use `/documentation/<path>` links in the site and relative file links in repository Markdown.

```bash
bun run dev:docs
```

Open **http://localhost:3002/documentation** and inspect the pages you changed. Start instructions
with prerequisites and a clear outcome, identify the working directory for commands, and use
complete examples with clearly marked placeholders. Check claims against the current source code.

Search data and `llms.txt` exports are generated by the docs build; edit their MDX sources instead
of committing generated output. For MCP capability changes, update both the public MCP guide and
[ADR-0001](docs/adr/0001-mcp-security-architecture.md); the catalog consistency tests check both.

## Validate your changes

For documentation changes:

```bash
bun run --filter @durabull/docs typecheck
bun run build:docs
bun test packages/mcp/src/tools/docs-consistency.test.ts
git diff --check
```

Check internal links, code-block rendering, sidebar placement, and copyable commands. A successful
MDX build does not prove that a setup command is accurate.

For application changes, run the affected workspace's tests as well as the repository checks:

```bash
bun run lint
bun run format:check
bun run typecheck
bun run build
```

The API uses `bun run --filter @durabull/api test`; the web app uses
`bun run --filter @durabull/web test:unit`. Browser tests run with `bun run test:e2e` and need the
PostgreSQL/Redis setup described by the CI workflow. Use disposable data for tests and seed scripts.

## Prepare a pull request

Keep the change focused. Explain the problem, the resulting behavior, and how you verified it.
Include known test failures or environment limitations. Use a descriptive title such as
`docs: clarify Docker persistence and setup`.

If your work follows a local issue or PRD, reference its path. Repository planning and triage use
[local Markdown issues](docs/agents/issue-tracker.md); external pull requests are not the issue tracker.
Keep planning notes separate from the public documentation.

Before submitting, review `git diff` and `git status` for unrelated edits, secrets, and generated
artifacts. For changed instructions, verify them from a clean setup where practical.
