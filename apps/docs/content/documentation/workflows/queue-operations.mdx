## Route Scope

Queue detail route:

- `/$orgSlug/c/$connectionId/queues/$queueName`

This page combines queue summary, jobs table, and scheduled-job tab.

## Available Queue Controls

### Pause/Resume Queue

- `POST /api/c/:connectionId/queues/:queueName/pause`
- `POST /api/c/:connectionId/queues/:queueName/resume`

Pause prevents workers from picking up new jobs; jobs already active continue processing. Use it
during downstream outages or maintenance, and resume after the underlying issue is resolved.

### Flow Controls (Global Concurrency and Rate Limit)

- `GET /api/c/:connectionId/queues/:queueName/flow-controls`
- `PUT /api/c/:connectionId/queues/:queueName/flow-controls`
- `POST /api/c/:connectionId/queues/:queueName/flow-controls/clear-rate-limit`

Flow controls are queue-wide limits stored in the BullMQ queue meta hash. Every worker on the
queue reads them from Redis, so you can throttle a queue during an incident or protect a
downstream API's quota without redeploying workers.

- **Global concurrency** caps how many jobs process at once across all workers, regardless of
  each worker's own `concurrency` option.
- **Global rate limit** caps how many jobs start per time window across all workers. A worker
  that sets its own `limiter` option keeps its own `duration` and uses the queue-wide `max`
  with it, so leave `limiter` off your workers when you want the window set here to apply.

In the UI, open the queue actions menu and choose **Flow controls**. The dialog shows how many
jobs are active against the concurrency cap and whether a rate-limit window is currently open.
When limits are set, the queue header shows a summary such as `8 concurrent · 120/min`; click it
to edit.

`PUT` accepts either field or both. An omitted field stays unchanged and `null` removes the limit:

```json
{ "globalConcurrency": 8, "globalRateLimit": { "max": 120, "durationMs": 60000 } }
```

- `globalConcurrency`: integer from `1` to `100000`
- `globalRateLimit.max`: integer from `1` to `1000000`
- `globalRateLimit.durationMs`: integer from `1` to `86400000` (24 hours)

Every flow-controls route returns the current state:

- `globalConcurrency` and `globalRateLimit` (`null` when not set)
- `rateLimited` and `rateLimitTtlMs`: whether the queue-wide rate limit or a manual
  `rateLimit()` call is holding workers back, and for how long. A worker's own `limiter` option
  is not stored in Redis, so throttling by that limiter alone is not reported.
- `isMaxed`: whether active jobs have reached the concurrency cap
- `activeCount`

`clear-rate-limit` ends the current window. Workers that already saw it resume when their own
back-off ends, which BullMQ caps at the worker's `maximumRateLimitDelay` (30 seconds by
default). The configured limit stays in place and applies again from the next job. To remove the
limit, send `{ "globalRateLimit": null }`.

Changing the rate limit to a shorter window also shortens a window that is already open, so the
new window applies right away rather than after the old one ends.

Limits take effect the next time a worker fetches a job; jobs already running are not
interrupted. Workers on BullMQ releases that predate queue-level limits ignore them, so confirm
your workers' BullMQ version before relying on them.

### Clean Queue by Status

- `POST /api/c/:connectionId/queues/:queueName/clean`
- Requires `status`; optional `gracePeriod` in milliseconds (default `0`) and `limit` (default `1000`).

Supported clean statuses are `completed`, `failed`, `delayed`, `paused`, `waiting`, `active`,
and `prioritized` (mapped internally to BullMQ equivalents).

### Purge Queue Jobs (Guarded + Multi-Status)

- `POST /api/c/:connectionId/queues/:queueName/purge`
- Requires:
  - `confirmName` (must exactly match queue name)
  - `statuses` (one or more specific statuses, or `["all"]`)

Purge removes jobs in the selected states. It excludes `waiting-children` and does not remove schedulers.

Operational behavior:

- users can select any status combination (`waiting`, `active`, `delayed`, `completed`, `failed`, `paused`, `prioritized`)
- users can choose all supported statuses via `statuses: ["all"]`
- confirmation input only authorizes purge when exact queue name is entered

Response includes:

- `statusesPurged`
- `totalRemoved`
- `removedByStatus`
- `removedJobIdsSample` (sample only)

Optional `keepMostRecent` preserves the newest N jobs across the selected statuses (default `0`,
maximum `1000000`). Locked jobs may remain or cause a conflict, depending on the removal path.
A purge is not atomic: a `409` can occur after some jobs have already been removed.

### Purge Flow in the UI

1. Open queue detail settings menu.
2. Choose **Purge Jobs**.
3. Select one or more statuses, or **All jobs**.
4. Type exact queue name to enable the destructive action.
5. Submit purge and verify updated queue counts.

### Obliterate Queue

- `POST /api/c/:connectionId/queues/:queueName/obliterate`

Forcefully removes queue data and its discovery index entry. Unlike the guarded delete endpoint,
this endpoint does not require `confirmName` or check job counts. Stop producers and workers
before using it; a running application can recreate the queue.

### Delete Queue (Guarded)

- `DELETE /api/c/:connectionId/queues/:queueName`
- Requires `confirmName` that must match queue name
- Refuses deletion while waiting, active, delayed, failed, paused, or prioritized jobs remain.
- Completed jobs do not block deletion; deletion removes their data too.
- The pre-flight check does not count `waiting-children`; inspect dependent jobs separately.

Use pre-flight check route:

- `GET /api/c/:connectionId/queues/:queueName/can-delete`

## Safe Deletion Procedure

1. Stop producers, remove schedulers that would create new jobs, and stop workers after active jobs finish.
2. Purge or clean the supported states, then inspect and handle `waiting-children` separately.
3. Confirm queue is deletable via `can-delete`.
4. Delete with exact queue name confirmation.
