---
title: How to Use Durabull
description: Connect your Redis instance, find your queues, and investigate your first failed job.
---

Durabull connects to Redis to inspect and manage the jobs your BullMQ application creates.
It does not run your workers. You can explore queues without changing worker code; throughput
charts need [BullMQ metrics enabled on workers](/documentation/workflows/bullmq-native-metrics).

## Get connected

1. Open [Durabull Cloud](https://app.durabull.io), install a
   [desktop app](/documentation/getting-started/desktop-apps), or follow the
   [self-hosted installation](/documentation/self-hosting/installation).
2. Sign in and create or select an organization when authentication is enabled. Authless mode
   creates a local organization automatically.
3. Select a Redis connection, or add one in **Settings → Connections** when UI management is enabled.
   Match the Redis database and BullMQ prefix used by your application; the default prefix is `bull`.
4. Open **Queues**. An empty Redis instance has no queues until your application creates them.
   If you expected queues, use [Connection Troubleshooting](/documentation/getting-started/connection-troubleshooting).

The Redis URL must be reachable from the Durabull API. For desktop, that is your workstation;
for Docker, it is the container; for Cloud, it is the hosted service.

## Investigate a failed job

1. Confirm the selected organization, connection, and environment.
2. Open a queue with failed jobs, then filter its jobs by **Failed**.
3. Open a job and read the failure reason, stack traces, data, and logs. Workers must write
   logs with `job.log`; console output does not automatically appear here.
4. Fix the cause in your application or its dependencies. Before retrying, consider whether
   the previous attempt may already have performed part of its work.
5. Retry the job and watch its state and new logs. If it stays waiting, confirm that a worker
   is listening to the same queue and prefix.

Use a development queue for your first drill. See
[Job Lifecycle and Debugging](/documentation/workflows/job-lifecycle-and-debugging) for editing,
retrying, and removing jobs.

## Find the right workspace

| Workspace | Use it to | Read next |
| --- | --- | --- |
| Queues | Compare current job counts and spot backlogs | [Queues Dashboard](/documentation/workflows/queues-dashboard) |
| Queue detail | Inspect jobs, metrics, and queue controls | [Queue Operations](/documentation/workflows/queue-operations) |
| Analytics | Compare throughput and fleet signals | [BullMQ Native Metrics](/documentation/workflows/bullmq-native-metrics) |
| Scheduled Jobs | Create and manage recurring job templates | [Scheduled Jobs](/documentation/workflows/scheduled-jobs) |
| Workers | See Redis clients and connection activity | [Workers Topology](/documentation/workflows/workers-topology) |
| Redis Keys | Inspect keys, values, and expiry | [Redis Key Explorer](/documentation/workflows/redis-key-explorer) |
| Alerts | Monitor failures and Redis pressure in the background | [Redis Health and Alerts](/documentation/workflows/redis-health-alerts) |

Queue pause stops workers from starting new jobs; active jobs can continue. Purge and delete
have confirmation steps. Obliteration is a separate destructive action without those safeguards.
Read [Queue Operations](/documentation/workflows/queue-operations) before removing queue data.

## Make future incidents easier

- Use [consistent queue and scheduler names](/documentation/workflows/naming-best-practices).
- Write [structured job logs](/documentation/workflows/log-formatting-and-highlighting).
- Route alerts to [webhooks](/documentation/integrations/webhooks) or
  [Linear](/documentation/integrations/linear).
- Use [Troubleshooting](/documentation/operations/troubleshooting) when a queue is missing,
  jobs remain waiting, or integrations fail.
